## 1. 先澄清“更多格式”

现有 HTTP/HTTPS 下载器已经可以下载任意文件类型，例如：

- 安装包：DMG、PKG、MSI、EXE、APK
- 压缩包：ZIP、7Z、RAR、TAR、GZ
- 磁盘和镜像：ISO、IMG
- 普通文件：PDF、音频、图片、模型、数据集

因此，如果 V2 只是增加这些文件扩展名，传输层不需要变化。真正需要扩展的是：

1. 流媒体播放列表：HLS `.m3u8`、DASH `.mpd`
2. 文件传输协议：FTP、FTPS、SFTP
3. P2P 协议：BitTorrent、Magnet
4. 多来源下载：Metalink、多镜像 URL 自动择优
5. 下载后的处理：合并音视频、转换容器、校验、解压

“下载后处理”不属于传输协议，不能和极速下载混成一个不可审计的大模块。

## 2. V2 产品目标

### 2.1 必须保持的体验

- 用户仍在主界面完成单任务下载。
- 服务器支持并行时，任务应尽量逼近可用带宽上限。
- 多协议共用同一套真实进度、速度、暂停、恢复和错误状态。
- 任何协议都不得伪造进度、速度、连接数或 ETA。
- 新增协议不能拖慢 HTTP/HTTPS 主路径。
- 关闭 QuickDL 后不得留下孤立代理、解析器或下载进程。

### 2.2 建议的 V2 成功标准

- HTTP 大文件尾段继续动态拆分，不再被最后一个慢连接长期拖住。
- HLS VOD 能选择正确码率、并行下载全部分片并检测缺失。
- FTP/FTPS 支持认证、Range 续传和 TLS 证书校验。
- 任一分段失败可自动重试并从已完成偏移继续。
- 进程被强制结束后，重新打开能恢复任务与分段状态。
- 完成后校验文件大小；有 ETag、Last-Modified 或校验和时执行一致性检查。
- 公网速度必须与相同 URL、相同网络下的 aria2c/浏览器或独立请求组对比后报告。

## 3. 功能分级

### 3.1 推荐 P0：实用的 V2

P0 的目标是让 V2 真正可用，而不是一次堆入所有协议。

| ID | 功能 | 理由 |
| --- | --- | --- |
| V2-01 | 协议检测与 Adapter 路由 | 后续所有格式的基础 |
| V2-02 | HTTP 分段失败自动重试 | 当前最明显的可靠性缺口 |
| V2-03 | SQLite 分段状态与重启恢复 | 极速下载必须能续传 |
| V2-04 | HTTP 动态块调度与慢尾再切分 | 解决最后 1% 拖慢整单 |
| V2-05 | HLS VOD `.m3u8` | 动漫/视频资源最常见格式 |
| V2-06 | HLS master playlist 码率选择 | 避免只下低清或多下不必要内容 |
| V2-07 | HLS 分片并发、失败重试、完整性检查 | HLS 的核心速度与正确性 |
| V2-08 | HLS AES-128 标准密钥获取 | 仅处理用户可访问内容 |
| V2-09 | FTP/FTPS 认证和续传 | libcurl 已有能力，新增成本低 |
| V2-10 | 下载完成后 SHA-256 计算 | 结果可验证 |
| V2-11 | 协议能力与失败原因可视化 | 用户能知道为什么没加速 |
| V2-12 | 代理对 HTTP/HLS/FTP 一致生效 | 不重复实现代理逻辑 |

### 3.2 P1：重量级协议

| ID | 功能 | 主要难点 |
| --- | --- | --- |
| V2-13 | BitTorrent `.torrent` | 分块验证、peer、tracker、DHT、做种策略 |
| V2-14 | Magnet URI | DHT 元数据交换、NAT、Peer 发现 |
| V2-15 | DASH `.mpd` | 时间轴、Representation、音视频轨道 |
| V2-16 | SFTP | SSH 认证、主机指纹、密钥存储 |
| V2-17 | Metalink/多镜像 | 来源测速、哈希校验和失败切换 |
| V2-18 | HLS 直播录制 | 无自然终点、分片滑动窗口 |
| V2-19 | 音视频合并/封装 | FFmpeg sidecar 与许可、CPU 调度 |
| V2-20 | 下载后自动解压 | 压缩炸弹、路径穿越和权限风险 |

### 3.3 明确不做

- 绕过付费墙、DRM、登录态、验证码、地域限制或访问控制。
- Widevine、PlayReady、FairPlay 解密。
- 网页视频嗅探、浏览器 Cookie 自动盗取。
- ED2K、迅雷私有协议和未公开协议逆向。
- 未经授权的内容站点解析规则。
- 移动端。

## 4. 推荐发布拆分

### V2.0

目标是“下载核心升级 + HLS + FTP/FTPS”：

- 协议 Adapter 架构
- HTTP 自动重试、持久化恢复、动态慢尾拆分
- HLS VOD
- FTP/FTPS
- SHA-256
- 统一真实速度和错误状态

### V2.1

- DASH
- SFTP
- Metalink/多镜像择优
- HLS 直播

### V2.2

- BitTorrent/Magnet
- 做种策略
- 端口映射和网络诊断

把 BT 放到独立的 V2.2 是有意设计。BT 不是“再加一种 URL”，而是新的网络生态、磁盘随机访问模型、连接信誉和长期后台状态。直接塞进 V2.0 会拖垮可靠性和安装包体积。

## 5. 架构

```text
输入
  ↓
Protocol Router
  ├─ HTTP / HTTPS Adapter
  ├─ HLS Adapter
  ├─ FTP / FTPS Adapter
  ├─ SFTP Adapter
  ├─ DASH Adapter
  └─ BitTorrent Adapter
  ↓
统一 Task Engine
  ├─ 分段/分片状态
  ├─ 并发预算
  ├─ 重试和退避
  ├─ 代理路由
  ├─ 真实进度与速度
  └─ SQLite 持久化
  ↓
落盘与校验
  ├─ 临时文件
  ├─ 完整性检查
  ├─ SHA-256
  └─ 原子重命名/合并
```

约束：

- 各 Adapter 只负责协议解析和任务计划，不直接控制 QML。
- 所有 Adapter 向 Task Engine 报告真实字节和状态。
- 代理由统一网络层注入，不在每个协议中重复实现。
- HTTP 主路径不得被 HLS、BT 等依赖影响。
- 协议模块可关闭；未启用的协议不加载相关网络或二进制依赖。

## 6. HLS VOD 需求

### 6.1 输入

- 单个 `.m3u8`
- master playlist 中用户选择的码率
- 默认选择“最高可用码率”，但必须在开始前展示分辨率和预计大小

### 6.2 下载

- 解析相对/绝对 URL、媒体序列、分片时长、初始化片段。
- 并发下载分片，默认 8 路，按服务器响应自适应到 4～16 路。
- 支持 `.ts`、fMP4 `.m4s`、AAC 和 WebVTT 字幕分片。
- 支持查询参数、重定向、自定义 Referer/Cookie 的用户明确配置。
- AES-128 密钥按 URI 获取；密钥不得写入日志。
- 分片缺失、0 字节、重复覆盖、序号错误必须被发现。

### 6.3 输出

- V2.0 默认输出为完整分片的无损合并文件或原始容器。
- 不声称“任意网站视频一键 MP4”。
- MP4 重封装作为 V2.1 的可选后处理，依赖 FFmpeg sidecar。
- 完成后输出分片数量、总时长、缺失检查结果和 SHA-256。

### 6.4 边界

- 仅支持用户可访问的 HLS 地址。
- 不处理 DRM、许可证服务器破解或登录态自动提取。
- 直播 m3u8 不进入 V2.0。

## 7. FTP / FTPS 需求

- 支持匿名与用户名/密码登录。
- 密码使用系统安全存储，不写入普通日志或 QSettings 明文。
- 支持 FTPS 显式 TLS，证书校验默认开启。
- 支持 SIZE、REST/Range 续传；服务器不支持时明确降级。
- 支持被动模式。
- 单连接是基线；支持服务器允许时的分块并行。
- 不把“支持 FTP”理解为支持任意非 HTTP 网页脚本。

## 8. BitTorrent/Magnet 审计

建议使用成熟的独立引擎，不自己实现 BT 协议。

候选：

- libtorrent-rasterbar
- 独立 aria2 BT 模式

必须解决：

- 分块 SHA-1 验证
- Tracker、DHT、PEX、Magnet 元数据
- Peer 连接和最大连接数
- 下载/做种比例
- 磁盘预分配与随机写入
- 防火墙、NAT、端口映射
- 版权和用户内容责任

BT 的速度不按“连接数越多越快”宣传。可用速度取决于 peer、做种、ISP、NAT 和 swarm 健康度。

## 9. 速度要求

### 9.1 HTTP

- 动态块而非固定长分段。
- 分段完成后继续领取新块。
- 慢连接剩余块可继续二分，避免尾段拖慢。
- 并发按吞吐和错误率渐升，不以硬打满连接为目标。
- 429/503/超时自动退避。

### 9.2 HLS

- 分片并发不能超过服务器承受范围。
- 小分片调度开销必须低，避免“并发很高但磁盘等待严重”。
- 分片下载速度按已写盘字节统计，不按请求发出量统计。

### 9.3 公平基准

同一份公网文件至少比较：

- QuickDL
- 浏览器
- aria2c 同连接数
- 16 个独立 Range 参考请求

报告必须包含：

- 网络类型和运营商
- 目标 URL 类型
- 文件大小
- 连接数
- 起止时间
- 平均速度和峰值速度
- 服务端响应码
- 是否有代理

## 10. 数据与恢复

SQLite 建议表：

```text
tasks
segments
http_validators
hls_segments
protocol_metadata
settings
```

任务恢复必须校验：

- 本地临时文件仍存在
- 文件大小与计划一致
- URL 最终地址或 ETag/Last-Modified 未变化
- 已完成分段连续且无重叠
- 协议配置版本一致

任一项不匹配时，不静默拼接；应提示重新验证或重新下载。

## 11. 安全边界

- 所有订阅、FTP 密码、HLS 密钥和其他凭证进入系统安全存储。
- URL、密钥、Cookie、Authorization 不进入普通日志。
- HLS 密钥只保存在内存或受保护临时位置，完成后清理。
- BT 默认关闭 DHT 入站监听，用户显式开启后再开放端口。
- 自动解压必须防止 Zip Slip、符号链接逃逸和压缩炸弹。
- 最终文件未完成前保持 `.part` 或工作目录形式。

## 12. 验收标准

### 12.1 V2.0 阻断项

| ID | 验收 |
| --- | --- |
| AC-01 | HTTP 任务中断网后自动重试，最终 SHA-256 正确 |
| AC-02 | HTTP 任务强制结束进程，重启后能从 SQLite 恢复 |
| AC-03 | 慢尾分段被重新切分，尾段额外等待明显缩短 |
| AC-04 | HLS master playlist 能列出码率并选择指定版本 |
| AC-05 | HLS 所有分片完整、顺序正确、无重复覆盖 |
| AC-06 | HLS 分片失败可重试，进度不倒退 |
| AC-07 | FTPS 证书错误默认拒绝，不能静默降级明文 |
| AC-08 | FTP/FTPS 断点续传后文件哈希正确 |
| AC-09 | 代理、直连和内置 mihomo 对 HTTP/HLS/FTP 一致生效 |
| AC-10 | 关闭 QuickDL 后无孤立 mihomo、FFmpeg 或下载子进程 |

### 12.2 性能门槛

- HTTP 16 路受控测试达到 aria2c 同条件吞吐的 85% 以上。
- 优化后目标达到 95% 以上。
- HLS 分片聚合速度达到同条件独立请求组的 85% 以上。
- 公网测试不得把局域网 354 MB/s 说成公网承诺。

## 13. 审计结论

### 推荐直接批准

- HTTP 可靠性升级
- SQLite 恢复
- HLS VOD
- FTP/FTPS
- 统一协议 Adapter
- SHA-256 与日志脱敏

### 需要单独批准

- BitTorrent/Magnet
- DASH
- SFTP
- HLS 直播
- FFmpeg 后处理
- 自动解压

### 默认决策

若用户没有指定其他优先级，V2.0 按以下顺序推进：

1. 先修 HTTP 重试、恢复和慢尾调度。
2. 再接 HLS VOD。
3. 再接 FTP/FTPS。
4. 所有功能通过验收后再进入 BT。

这能保证“支持更多格式”不是把一堆不稳定解析器塞进主界面，而是每个新增协议都达到真实进度、可暂停、可恢复、可验证、可测速。
